# Walmart Revenue Forecasting

A reproducible time-series forecasting pipeline for the Walmart Revenue Forecasting competition.

The project combines feature engineering, time-aware validation, LightGBM modeling, Optuna hyperparameter tuning, model ensembling, hierarchical reconciliation, and leakage/overfitting audits.

> **Final validation result:** Combined 3-fold RMSE = **6,360**, compared with **13,751** for the naive seasonal baseline (~53.7% lower RMSE).

**Validation improvement:** approximately **53.7% lower RMSE** than the naive seasonal baseline. The final ensemble used **83.0% Global LightGBM + 17.0% Per-Store LightGBM**, with the naive model receiving 0% weight.

---

## Competition Overview

This project was developed for the **[Walmart Revenue Forecasting Competition](https://www.kaggle.com/competitions/advanced-machine-learning-competition-2026-b-runi)**, a modified version of the **M5 Forecasting** dataset. The competition asks participants to forecast daily revenue for Walmart stores using historical store data and calendar/event information.

### Competition Context

- **Data source:** Modified M5 Forecasting dataset
- **Stores:** 10 individual Walmart stores plus an aggregate/all-stores hierarchy
- **Forecast horizon:** 1,012 submission entries
- **Target:** Daily store revenue
- **Evaluation metric:** Root Mean Squared Error (RMSE)
- **Exogenous information:** Calendar events that may affect retail demand
- **Forecasting task:** Produce a prediction for every store/date combination in the submission file

The competition also emphasizes hierarchical forecasting: predictions should be meaningful both at the individual-store level and at the aggregate level. Because RMSE is an absolute-error metric, stores with higher revenue baselines can have a larger effect on the final score. The aggregate/all-stores level also has an important influence on evaluation.

The submission format is:

```csv
id,prediction
0_20250101,100
0_20250102,200
0_20250103,100
0_20250104,100
...
```

Here, `id` is `{store_id}_{YYYYMMDD}`.

### Dataset Size and Modeling Data

The competition description specifies **18,766 training data points** in the provided training data and **1,012 forecast/submission entries**. The feature-engineering pipeline then removes the initial warm-up rows that do not have the required year-over-year lag history (`lag_364`, `lag_365`, and `lag_371`). This leaves **14,685 rows** in the generated training feature set used by the modeling stage.

---

## Project Overview

The objective is to forecast daily revenue for the competition forecast window while avoiding information that would not be available at prediction time.

The pipeline is organized into four main phases:

1. **EDA** — understand sales patterns and calendar effects.
2. **Feature engineering** — build time, lag, rolling, event, store, and interaction features.
3. **Modeling and tuning** — compare baselines and LightGBM variants, tune hyperparameters, and optimize an ensemble.
4. **Audit** — test feature ablations, leakage safety, and train/validation behavior.

The final forecast is generated for **Q4 2015 (October 1–December 31, 2015)**.

## How to Run

### 1. Optional: Exploratory Data Analysis

```bash
python eda.py
```

Generates diagnostic plots in `eda_output/`. This step is useful for understanding trends, seasonality, and event behavior, but it is not required to generate the final submission.

### 2. Feature Engineering

```bash
python features.py
```

This script:

- Loads the raw competition data.
- Builds a complete store/date time spine covering training and forecast periods.
- Creates date and cyclical time features.
- Creates short and long revenue lags.
- Creates rolling statistics.
- Adds calendar and holiday features.
- Adds store-level scale features.
- Adds interaction and year-over-year trend features.
- Writes the generated feature datasets and feature catalog.

The feature-generation stage creates a broad feature set (96 final feature columns in the generated feature dataset). For the direct forecast model, the pipeline applies an additional semantic safety whitelist and ultimately uses **79 forecast-safe features** in `models.py`.

Generated files include:

```text
features/train_features.csv
features/test_features.csv
features/feature_catalog.txt
```

### 3. Optional: Hyperparameter Tuning

```bash
python tune.py
```

Optuna searches LightGBM hyperparameters using two data-rich validation folds:

- Q4 2013
- Q4 2014

The search uses **60 trials**. In the recorded run, all 60 trials completed in **222 seconds**, with a best 2-fold RMSE of **5,087**.

The best configuration was:

```text
learning_rate       = 0.14755
num_leaves          = 32
min_child_samples   = 16
colsample_bytree    = 0.89318
subsample           = 0.88064
reg_alpha           = 1.1013
reg_lambda          = 0.80144
```

The result is saved to:

```text
best_lgbm_params.json
```

`models.py` automatically loads this file when it exists.

### 4. Train Models and Generate Submission

```bash
python models.py
```

This is the main pipeline. It:

1. Loads the tuned parameters when available.
2. Runs 3-fold Q4 cross-validation.
3. Trains a global LightGBM model and separate per-store LightGBM models.
4. Evaluates a naive seasonal baseline.
5. Optimizes ensemble weights using out-of-fold predictions.
6. Retrains final models on the full available training data.
7. Generates Q4 2015 predictions.
8. Applies hard zero overrides for store-closed holidays.
9. Reconciles the hierarchy so **store 0 = sum of stores 1–10**.
10. Saves the final competition submission and evaluation plots.

### 5. Optional: Leakage and Overfitting Audit

```bash
python audit.py
```

The audit performs:

- Feature ablation experiments.
- A systematic leakage audit.
- Train vs. validation RMSE analysis.
- Checks of feature safety for the full 92-day forecast window.

Use this when modifying the feature set or model configuration.

## Feature Engineering Strategy

The main challenge in this competition is that future revenue is unknown. Features therefore need to be useful while remaining available for the entire forecast horizon.

### Time Features

Examples include:

- year, month, day
- day of week
- week of year
- quarter
- weekend indicators
- month-start/month-end indicators
- day within quarter
- time index
- cyclical sine/cosine encodings

### Lag Features

The pipeline creates both short-term and long-term lags.

Short lags:

```text
7, 14, 21, 28, 35, 42, 56 days
```

Long, forecast-safe lags:

```text
92–98, 182, 364, 365, 371, 728–731 days
```

For the 92-day Q4 forecast, a lag must be at least 92 days to avoid referencing the unknown forecast period.

### Calendar-Shift-Aware Lag

A useful improvement was the `best_lag` feature:

```text
best_lag = max(lag_364, lag_365, lag_371)
```

This helps when a fixed 364-day offset maps a date to an unusual holiday in the previous year. The feature was introduced after observing a large holiday-related error and allows the model to select a stronger comparable historical reference.

### Rolling Features

Rolling means and standard deviations are generated for multiple window sizes. For the direct forecast model, the final whitelist uses **anchor-lag rolling features** so that the rolling windows remain entirely in known historical data.

### Event Features

The pipeline includes:

- Specific holiday/event indicators.
- Event categories.
- Days until the next event.
- Days since the last event.
- Pre/post holiday ramp windows.
- Black Friday and Cyber Monday indicators.
- Event × weekend interactions.

Christmas and New Year are treated as hard-closed days and are forced to zero in the final prediction stage.

### Store Features

Store-level information includes:

- Region encoding.
- Store revenue mean and standard deviation.
- Relative lag scale features.
- Store ID as a categorical input to the global model.

## Leakage Prevention

Leakage control was a major part of the pipeline.

The leakage audit uses the rule that a feature for forecast day `D` must depend only on information available before the forecast begins.

Features intentionally excluded from the direct forecasting model include examples such as:

- Short lags that become dependent on predictions/unknown future values later in the forecast.
- Regular rolling statistics that can include in-period actuals during validation.
- `expanding_mean` when it would expose validation-period information.
- `rolling28_vs_store_mean`, because it depends on a leaky rolling feature.
- `yoy_delta_364 = revenue - lag_364`, because it is target-derived.

This is why the modeling stage uses a semantic feature whitelist instead of simply passing every generated column to LightGBM.

## Modeling Approaches

### Naive Baseline

The baseline uses the previous year's comparable revenue (`lag_364`). It provides a simple seasonal reference point.

### Global LightGBM

One LightGBM model is trained jointly on stores 1–10.

The model uses store information as a categorical feature and uses revenue-scale sample weights so larger stores have a greater influence on the training objective.

### Per-Store LightGBM

A separate LightGBM model is trained for each of stores 1–10.

This allows each model to specialize in store-specific behavior.

### Hierarchical Reconciliation

Store 0 is not directly modeled in the final approach. Predictions for stores 1–10 are summed to produce store 0:

```text
store_0 = store_1 + store_2 + ... + store_10
```

This guarantees consistency across the hierarchy.

## Validation Strategy

The final modeling pipeline uses three Q4 validation folds:

| Fold | Training cutoff | Validation window |
|------|------------------|-------------------|
| Q4 2012 | 2012-09-30 | 2012-10-01 → 2012-12-31 |
| Q4 2013 | 2013-09-30 | 2013-10-01 → 2013-12-31 |
| Q4 2014 | 2014-09-30 | 2014-10-01 → 2014-12-31 |

This was chosen instead of random cross-validation because the task is a time-series forecasting problem.

For tuning and ensemble-weight optimization, the more data-rich Q4 2013 and Q4 2014 folds were used. Q4 2012 is still reported as an independent validation fold, but it was excluded from the tuning/weight search because its smaller training history represents a different information regime.

## Validation Results

Lower RMSE is better.

| Model | Q4 2012 | Q4 2013 | Q4 2014 | Combined |
|------|--------:|--------:|--------:|---------:|
| Naive | 16,314 | 12,612 | 11,920 | **13,751** |
| LGBM Global | 8,609 | 5,565 | 4,708 | **6,513** |
| LGBM Per-Store | 6,524 | 6,270 | 7,055 | **6,624** |
| Ensemble | 8,159 | 5,575 | 4,869 | **6,360** |

The final ensemble reduces combined RMSE from **13,751 to 6,360**, an improvement of approximately **53.7%** over the naive baseline.

### Ensemble Weights

The optimized weights were:

```text
Naive          0.0%
LGBM Global   83.0%
LGBM Per-Store 17.0%
```

The result indicates that the global model carried most of the predictive signal, while the per-store models added a smaller but useful complementary contribution.

## Changing the Pipeline

| Goal | File to edit |
|------|--------------|
| Change data location | `config.py` |
| Add/change feature calculations | `features.py` |
| Change the safe model feature whitelist | `models.py` / `tune.py` |
| Change tuning budget | `tune.py` (`N_TRIALS`, `TIMEOUT`) |
| Change model ensemble | `models.py` (`MODEL_COLS`) |
| Change ensemble-weight folds | `models.py` (`_opt_fold_names`) |
| Run leakage/ablation tests | `audit.py` |

When changing features, keep the safe-feature definitions in `features.py`, `tune.py`, and `models.py` synchronized.
